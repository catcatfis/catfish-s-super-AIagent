# yu-ai-agent 各包学习顺序与建议

> 面向 Spring AI 初学者/复习者：按"先跑通 → 理解核心抽象 → 逐层叠加高级能力"的顺序梳理本项目的包结构与学习路径。每个阶段给出核心类、学习重点和自测问题，确保学一个会一个。

## 一、项目全景（先建立地图）

```
com.yupi.yuaiagent
├── YuAiAgentApplication      # Spring Boot 启动类
├── demo                      # ★ 第 1 站：AI 调用入门示例（invoke / rag）
├── app                       # ★ 第 2 站：核心应用层（LoveApp / TravelApp 六大能力）
├── chatmemory                # 会话记忆持久化
├── advisor                   # Advisor 拦截器（日志 / 推理增强）
├── rag                       # RAG 检索增强（文档加载 / 向量库 / 查询优化）
├── tools                     # Tool Calling 工具（文件/搜索/PDF/天气汇率…）
├── agent                     # ★ 第 3 站：自主智能体（ReAct 循环 / YuManus）
├── controller                # HTTP 接口层
├── config / constant         # 配置与常量
```

三条主线：**app（应用能力）→ rag/tools（增强能力）→ agent（自主智能体）**。demo 是热身，controller 是验证手段。

## 二、推荐学习顺序

### 第 1 站：demo —— AI 调用是怎么发生的？

| 顺序 | 类 | 内容 |
|---|---|---|
| 1 | `demo/invoke/TestApiKey` | 验证 DashScope API Key 是否可用 |
| 2 | `demo/invoke/HttpAiInvoke` | 裸 HTTP 调用大模型（最底层，理解请求长什么样） |
| 3 | `demo/invoke/SdkAiInvoke` | 官方 SDK 调用（感受封装带来的便利） |
| 4 | `demo/invoke/SpringAiAiInvoke` | **Spring AI ChatClient 调用**（本项目的主力方式） |
| 5 | `demo/invoke/LangChainAiInvoke` | LangChain4j 对比（知道即可） |
| 6 | `demo/invoke/OllamaAiInvoke` | 本地模型调用（了解换模型只需换依赖和配置） |

**学习建议**：重点对比 2 → 4，同一个事情从"手写 HTTP"到"ChatClient 一行调用"的演进，你就理解了框架封装的意义。LangChain4j 那个只做了解，不必深究。

**自测**：能说清 ChatModel 与 ChatClient 的区别吗？（前者是模型抽象，后者是带 Advisor/记忆/工具编排的高级封装）

### 第 2 站：app + advisor + chatmemory —— 对话应用的骨架

先读 **`app/LoveApp`**（教程原版，注释全），再读 **`app/TravelApp`**（复刻 + 自主扩展，面试素材）。每个 App 覆盖六大能力，按方法顺序读：

| 顺序 | 方法 | 能力 | 关键依赖（顺藤摸瓜去读） |
|---|---|---|---|
| 1 | `doChat` / `doChatByStream` | 基础对话 + SSE 流式 | `advisor/MyLoggerAdvisor`（拦截请求响应，理解 Advisor 链） |
| 2 | 构造方法 | 系统提示词 + 会话记忆 | `chatmemory/FileBasedChatMemoryRepository`（Kryo 文件持久化，重启不丢） |
| 3 | `doChatWithReport` | 结构化输出（entity → record） | 无 |
| 4 | `doChatWithRag` | RAG 知识库问答 | rag 包（下一站） |
| 5 | `doChatWithTools` | Tool Calling | tools 包（第 4 站） |
| 6 | `doChatWithMcp` | MCP 协议调用 | 外部 MCP 服务配置 |

**学习建议**：
- 两个 App 对比着读：TravelApp 的差异点（旅行专属工具 travelTools、TravelReport、文件记忆独立目录）就是"从复刻到自主扩展"的证据，面试时讲这些差异最加分。
- `advisor/ReReadingAdvisor`（Re2 推理增强）做了解即可，知道 Advisor 可以改写 prompt 就行。
- 重点理解 `MessageChatMemoryAdvisor` 如何用 `CONVERSATION_ID` 参数区分多轮会话。

**自测**：SSE 的四种返回方式（String Flux / ServerSentEvent / SseEmitter）各自适用什么场景？

### 第 3 站：rag —— 检索增强全链路

按数据流向读：**文档 → 切分/富化 → 向量化入库 → 查询优化 → 检索增强**。

| 顺序 | 类 | 内容 |
|---|---|---|
| 1 | `rag/LoveAppDocumentLoader` | Markdown 文档加载（ResourcePatternResolver + MarkdownDocumentReader） |
| 2 | `rag/MyTokenTextSplitter` / `MyKeywordEnricher` | 文档切分与关键词富化（ETL） |
| 3 | `rag/LoveAppVectorStoreConfig` | SimpleVectorStore 内存向量库 + 启动时灌库 |
| 4 | `rag/PgVectorVectorStoreConfig` | PgVector 生产级向量库（当前注释，需 PG 环境） |
| 5 | `rag/QueryRewriter` | 查询重写（改写口语问题为适合检索的问题） |
| 6 | `rag/LoveAppContextualQueryAugmenterFactory` | 空上下文兜底话术 |
| 7 | `rag/LoveAppRagCustomAdvisorFactory` | 组装：DocumentRetriever（阈值/TopK 调优）+ QueryAugmenter |
| 8 | `TravelAppRagCustomAdvisorFactory` / `TravelAppDocumentLoader` / `TravelAppVectorStoreConfig` | 旅行版三件套，验证"知识库隔离" |
| 9 | `demo/rag/MultiQueryExpanderDemo` | 多查询扩展（了解） |

**学习建议**：
- 知识库文档在 `src/main/resources/document/` 下，love 与 travel 两个目录隔离——**改完文档要重启才生效**（启动时一次性加载），这是初学最常踩的坑。
- 对比第 6、7 步与裸 `new QuestionAnswerAdvisor(vectorStore)` 的区别：调优（similarityThreshold/topK）和空结果兜底是生产 RAG 的两个基本要求。
- `LoveAppRagCloudAdvisorConfig`（云知识库）做了解即可。

**自测**：检索结果为空时，用户看到什么？由哪个类决定？（`ContextualQueryAugmenter` 的 emptyContextPromptTemplate）

### 第 4 站：tools —— Tool Calling

| 顺序 | 类 | 内容 |
|---|---|---|
| 1 | `tools/WebSearchTool` | 最典型的 @Tool 注解工具（HTTP + 参数校验） |
| 2 | `tools/TravelInfoTool` | 旅行专属（Open-Meteo 天气 + 汇率，免 API Key，可直接跑） |
| 3 | `tools/PDFGenerationTool` | iText 生成 PDF（中文内置字体） |
| 4 | `tools/FileOperationTool` / `ResourceDownloadTool` / `TerminalOperationTool` / `TerminateTool` | YuManus 的手脚（文件/下载/终端/终止） |
| 5 | `tools/ToolRegistration` | 工具集中注册（allTools / travelTools 两个 Bean） |

**学习建议**：
- 先读懂前两个，`@Tool` + `@ToolParam` 的写法就完全掌握了；其余工具扫一遍即可。
- 注意 `TerminateTool` 的特殊性：它是给自主智能体"主动喊停"用的，只有 agent 场景才有意义。
- 动手实验：仿照 TravelInfoTool 写一个自己的工具（如景点门票查询），注册进 travelTools 跑通 `/ai/travel_app/chat/tools`，这是掌握 Tool Calling 最快的路径。

**自测**：模型并不真的"执行"你的 Java 方法，它做的是什么？（输出结构化的工具调用请求，由框架执行后把结果回传给模型）

### 第 5 站：agent —— ReAct 自主智能体（压轴）

| 顺序 | 类 | 内容 |
|---|---|---|
| 1 | `agent/BaseAgent` | 状态机 + 步数控制 + run/runStream 主循环 |
| 2 | `agent/ReActAgent` | think / act 抽象（ReAct 模式：推理 + 行动交替） |
| 3 | `agent/ToolCallAgent` | think/act 的工具调用实现（自维护消息上下文，禁用内置工具执行） |
| 4 | `agent/YuManus` | 通用智能体（组合全部工具） |
| 5 | `agent/TravelPlanAgent` | 旅行行程规划智能体（复刻 YuManus 结构 + 旅行系统提示词 + 强制生成 PDF，面试素材） |
| 6 | `agent/model/AgentState` | 状态枚举 |

**学习建议**：
- 这是全项目的精华，务必按继承链自底向上读。搞懂 `ToolCallAgent.think()` 里"禁用内置工具执行、自己维护消息列表"这一设计，就理解了 agent 与普通 Tool Calling 对话的本质区别。
- **坑**：BaseAgent 有可变状态，每次请求必须 new 新实例（看 AiController 的写法），不能注册为单例 Bean。
- TravelPlanAgent 是"学完就能讲"的素材：它证明了你能在 ReAct 框架上通过提示词工程定制垂直领域智能体。

**自测**：YuManus 一次任务的执行流程是什么？什么时候停？（循环 think→act，调 terminate 或达到 maxSteps）

## 四、三条主线的心法

1. **app 层是"编排"**：六大能力（对话/SSE/结构化/RAG/工具/MCP）本质都是"ChatClient + 不同 Advisor/工具组合"，理解了组合方式就能举一反三。
2. **rag 和 tools 是"给模型外挂能力"**：rag 给它私有知识，tools 给它行动力；两者都以 Advisor 或注解的形式挂进 ChatClient。
3. **agent 是"把模型变成循环系统"**：有了 think→act 循环 + 状态机 + 终止条件，模型才能自主完成多步任务——这是从"聊天机器人"到"智能体"的分水岭。
